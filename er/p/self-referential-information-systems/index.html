自指问题的信息系统

循环依赖、死锁、启动与反馈

识别不同类型的自指与循环结构，并从防御和攻击两端设计处理机制。

By Ruishen•2026年7月29日•3 min read

定义与识别

“钥匙被锁在盒子里”首先描述的是一种访问条件依赖于访问结果的结构：

取得钥匙 ⇒ 先打开盒子， 打开盒子 ⇒ 先取得钥匙。

它可能属于自指、循环依赖、死锁、启动问题、协调陷阱或正反馈，但这些术语不能互换。自指本身也不必然产生悖论；有些自指句无害，有些矛盾甚至可以在严格意义上没有直接自指。1 Curry 悖论还表明，即使没有显式否定，自指与蕴含规则的组合也可能引出爆炸性结果。2

“死锁”的必要条件

计算机系统中的经典死锁分析通常考察四个条件：互斥、持有并等待、不可抢占和循环等待。3 仅仅画出一个环还不足以证明无解；若资源可复制、可抢占、有超时或存在外部初始条件，循环可以被打破。

图论识别

把对象、资源或命题作为节点，把“必须先满足”作为有向边：

flowchart LR
    A["取得钥匙"] --> B["打开盒子"]
    B --> A
    X["外部钥匙/破拆/托管"] -. 打断依赖 .-> B

识别流程：

  1. 明确节点是资源、权限、知识、证明还是参与者；
  2. 给每条边写出精确前置条件；
  3. 查找强连通分量；
  4. 检查环内是否有初始资源、超时、替代路径或可放松条件；
  5. 区分“暂时等待”“稳定均衡”“不可计算”“逻辑矛盾”和“制度性准入障碍”。
为什么不能把所有闭环都归为 Gödel’s Incompleteness

Gödel’s Incompleteness Theorems 适用于满足特定表达能力、有效公理化和一致性条件的形式系统。它说明这类系统存在系统内部不可判定的命题，并对系统证明自身一致性施加限制；它不推出“任何含反馈的组织问题都无解”，也不等于“解决循环依赖必须升维”。

工程死锁可由资源调度解决，双边市场可由补贴启动，控制系统常依赖反馈才能稳定。把它们全部称为哥德尔问题，会丢失真正的必要条件与可操作解法。4

认知闭环：是否存在“无噪声认知”

在实践层面，答案应当是：不能把自身认知视为无噪声观察器。人既处理信息，也通过注意、记忆、语言、目标和行动改变未来输入；过滤器又会决定哪些错误能够被看见。

但这不是一个已由单一定理证明的“人类绝对不可能无偏”命题。更准确的边界是：

  • 有限观察与有限计算使剩余不确定性长期存在；
  • 认知偏差不能靠自我宣告完全消除；
  • 外部记录、独立复核、实验和概率校准可以降低而非归零误差；
  • “我已经纠偏”本身也需要外部证据。

在人机协同系统中，自指风险进一步增加：人用 LLM 生成资料，LLM 又以这些资料作为来源；模型评价自己的答案，人再以模型评分作为批准理由。防御要求保留真实世界锚点、不同生成机制的独立评价者和明确的人工责任。

防御端：如何切入并尝试处理

1. 重写前置条件

把“必须”拆为：

  • 逻辑必要；
  • 法律或制度要求；
  • 当前技术限制；
  • 成本偏好；
  • 参与者策略；
  • 习惯性假设。

很多“无解”来自把可谈判条件误写成逻辑必然。

2. 引入最小外部种子

启动系统不一定需要完整外部替代，只需足以产生第一轮内部能力的种子：

  • 固件启动操作系统；
  • 交叉编译器生成自举编译器；
  • 平台对一侧用户补贴，形成最小网络；
  • 培训项目提供模拟经验，降低“工作需要经验”的准入障碍；
  • 第三方托管在双方同时履约时释放资源。

双边市场研究说明，一侧参与度会改变另一侧价值，平台常通过不对称定价和启动策略处理鸡蛋—母鸡问题。5

3. 破坏死锁条件

条件防御动作
互斥复制资源、共享只读版本、拆分锁粒度
持有并等待统一申请、释放后重试、排序获取
不可抢占超时、租约、回滚、管理员接管
循环等待全局资源顺序、依赖图检测、禁止成环

4. 建立层级与元语言

语义悖论常通过区分对象语言与元语言、限制自我应用或采用显式/隐式层级处理。1 在组织中对应：执行者不能单独定义自己的合规标准，模型不能只用自己的输出证明自身正确，审计规则应由独立层维护。

5. 寻找固定点或允许迭代

并非所有循环都要切断。有些系统需要找到稳定状态：

xt+1 = f(xt).

可检查：是否收敛、是否有多个固定点、初值是否决定结果、扰动会否放大。若收敛条件不明，应设置迭代上限、停止准则和安全区间。

6. 放松、分阶段或随机启动

  • 把“必须完全满足”改成可接受阈值；
  • 将大承诺拆成可逆阶段；
  • 同步宣布多方同时进入；
  • 在对称均衡间使用透明随机机制；
  • 为早期参与者提供有期限且可退出的补偿。

7. 记录未解性类型

处理失败时，至少标注：

  • 缺资源；
  • 缺权限；
  • 缺共同知识；
  • 激励不相容；
  • 计算不可行；
  • 形式不可判定；
  • 价值冲突。

不同类型需要不同工具，不能统一用“升维”代替分析。

攻击端：如何设计

本节用于红队、博弈设计和韧性测试。不得在安全关键系统、公共服务或他人真实账户中制造未授权死锁。

1. 设计循环前置条件

在封闭模拟中，可构造：

  • A 的批准依赖 B，B 的批准依赖 A；
  • 每个参与者都等待别人先披露信息；
  • 验证工具只能由待验证对象提供；
  • 解锁权限需要使用被锁资源；
  • 模型输出被重新作为自身真实性证据。

测试目标是观察系统能否识别环、拒绝自证并触发外部复核。

2. 设计协调陷阱

在市场或组织仿真中设置：

  • 只有参与人数达到阈值才有正收益；
  • 早期参与者成本高、后期参与者搭便车；
  • 两侧用户都等待另一侧先形成规模；
  • 信息披露只有在他人披露后才有价值。

攻击端可以通过承诺、默认选项、阶段补贴或共同知识信号改变均衡；防御端则审查补贴退出后系统是否自持。

3. 设计递归验证陷阱

常见形式：

  • “该来源可信，因为它引用了自己的评级”；
  • “模型正确，因为另一个同源模型同意”；
  • “规则合法，因为规则授权了制定者”；
  • “身份真实，因为证明材料由同一身份签发”。

红队应追踪信任根，检查是否存在独立锚点、密钥层级和撤销机制。

4. 设计战略等待

让每方认为“先行动者暴露更多、后行动者占优”，即可形成等待均衡。合法的谈判设计可利用截止时间、分阶段交换和托管降低这种风险；恶意制造虚假截止时间或隐瞒关键退出成本属于操纵。

5. 攻击模板

目标：让系统进入循环等待或自证
节点：参与者 / 资源 / 权限 / 命题
依赖边：每个节点需要什么前置条件
隐藏假设：哪些边被包装成“当然如此”
维持条件：互斥、不可抢占、信息不对称、协调阈值
外部解法：超时、托管、替代资源、元层审查
成功指标：检测时间、恢复时间、损失、错误升级率
安全边界：仅在沙箱内，材料清楚标记，结束后清理

接口与工作机制

自指问题可以嵌入五模块：

模块典型自指风险防御接口
信源来源用自己的结论证明自己可靠独立信任根与来源图
发送器定义通过自身表述获得合法性对象语言/元语言分层
噪声过滤器训练于自己过滤后的数据保留未过滤基准与审计样本
接收器模型用自己的解释验证输入竞争模型与外部测试
信宿决策结果改变后续数据并自我强化反事实、随机试验与反馈控制

最小处理流程

  1. 画依赖图；
  2. 标记环和非良基链；
  3. 检查环是否真的满足无解条件；
  4. 选择打断、分层、外部种子、固定点或协调机制；
  5. 预设超时、回滚和责任主体；
  6. 观察干预是否只是把循环转移到更高层；
  7. 把新的依赖关系写回系统文档。
